# 올시즌 기록 갱신 · Jev → Codex 자연어 질의 구현기획

작성: 2026-10-24 KST. 상태: 검토용 기획. 코드 구현·운영 변경·유료 호출·스케줄 등록은 미실행.

## 목표와 확정 요구

- 매일 한국시간 15:00, 18:00 두 번 수집 작업을 시작하고 검증된 완료 경기만 기록에 공개한다.
- 최초 실행에서 2026–27 시즌 개막부터 누락된 DAL 경기를 보충한다. 사용자가 언급한 2경기는 공급자 경기 장부와 대조하며 개수를 고정하지 않는다.
- 올시즌 기록을 경기 상세·선수 기록·시즌·순위·비교·자연어 검색에서 동일하게 조회한다.
- 자연어 해석은 Jev를 우선하고, 지원 범위 안에서 해석이 어려운 질문은 Codex 모델로 보완한다. 단순 검색의 기존 규칙 경로는 유지한다.
- 수치 계산은 서버 DB가 담당하고 모든 답변에 적용 조건·기록 기준 시점·출처를 표시한다.

## 현행 근거와 전제

- `scripts/records/collect.py`: 고정 역사 자료 수집용. 최신 시즌 지속 갱신용이 아니다.
- `scripts/records/database.mjs`: release마다 전체 기록을 복제하고 검증 후 current_release를 변경한다.
- `ruby/app/services/records/query_interpreter.rb`: 규칙 및 Jev Choice 구현. 팀 승패·팀 통계·날짜 범위 등은 현행 거절 대상이다.
- `ruby/app/services/records/repository.rb`: release에 고정한 읽기 전용 집계와 캐시가 구현돼 있다.
- `vercel.json`에는 기록 스키마용 정기 갱신이 없다. 기존 팬 화면 점수 API와 역사 기록 저장은 별개다.
- Ruby는 로컬 구현 기준이며 운영 전환 여부는 별도 확인 대상이다. 스케줄러는 실제 운영 DB와 앱을 확인한 뒤 하나만 활성화한다.
- 아래 설계는 Rails 기록 서비스 기준이다. 운영이 Next인 경우 같은 snapshot 계약을 TS repository에도 적용한 후 공개한다.

## 데이터 수집과 공개

### 시간과 범위

| KST 시작 | UTC 시작 | 처리 |
|---|---|---|
| 매일 15:00 | 매일 06:00 | 신규 완료 경기와 최근 정정 수집 |
| 매일 18:00 | 매일 09:00 | 늦게 끝난 경기·미확보 기록·정정 재확인 |

- 타임존은 Asia/Seoul로 명시한다. UTC cron 표현식은 `0 6,9 * * *`다.
- 지정 시각은 작업 시작이다. 정상 공급 응답 기준 10분 내 공개를 초기 목표로 두고 표본 측정 후 확정한다.
- 최근 7일을 재조회하며 마지막 성공 이후 누락 구간과 미완료·기록 미확보 경기 큐도 재처리한다. 장기 장애로 7일 이상 누락돼도 회복해야 한다.
- 무경기일은 성공한 무변경 실행으로 기록한다. 원천 수집 시각이 달라도 내용이 같으면 새 기록 버전을 만들지 않는다.
- 진행 중·연기·취소는 상태로 구별하며 선수 평균·승패 집계에 포함하지 않는다. 늦은 완료는 다음 정기 실행에서 반영한다.
- 18시 이후 확정된 장기 정정은 7일 재조회 또는 별도 기간 지정 보충 명령으로 처리한다.

### 원천 선정과 검증

1. NBA 공식 기록 경로를 우선 후보로, 기존 ESPN 연결을 대안 후보로 평가한다. 현재 응답·필드 충족·저장/표시 이용조건·접근 안정성을 검증한 후 공급자를 확정한다. 앞선 NBA CDN 공개 조회는 403이었으므로 정상 접근을 전제하지 않는다.
2. 경기 장부, 양팀 박스스코어, 선수 참여 상태·선발·분·슈팅·리바운드·어시스트 등 기존 필드 매핑을 만든다. 제공되지 않는 심화 지표는 NULL과 coverage로 표시한다.
3. NBA ID와 공급자 ID 대응표를 둔다. 이름만으로 신규 선수·경기를 자동 병합하지 않는다. 미확정 매핑은 해당 경기를 검수 대기시킨다.
4. 시즌은 2026–27 → 시작연도 2026으로 저장한다. 정규·프리시즌·PO·컵 결승을 구분한다.
5. 양팀 최종 점수와 팀 기록, 선수 행의 중복·참조·NULL/DNP를 검증한다. 선수 합계와 팀 전용 통계 차이는 원천 의미를 보존한다.
6. 원본 해시·수집 시각·정정 전후를 보관하고 검증 통과 결과만 원자적으로 공개한다. 실패한 실행은 기존 공개 데이터를 유지한다.

### 저장과 일관성

- 과거 전체 release는 고정 기반으로 유지한다. 신규 올시즌 데이터는 변경된 경기별 불변 revision으로 저장한다.
- 공개 snapshot은 `baseReleaseId + 경기별 revision 목록`을 참조한다. 기반에 존재하는 경기의 정정은 같은 내부 game ID로 덮어보는 우선순위를 정하며 중복 집계하지 않는다.
- snapshot마다 선수·팀·출처·coverage 참조도 고정한다. 새 선수 목록과 시즌 카탈로그가 같은 snapshot에서 보이게 한다.
- 수집 중에는 비공개 staging에 작성하고 모든 검증 후 현재 snapshot 포인터 하나를 교체한다. 예전 URL과 서명된 검색 결과는 예전 snapshot을 계속 조회한다.
- 기존 release ID 형식과 API를 조용히 재정의하지 않는다. 새 snapshot 식별자·검증기·API 계약을 버전 구분하고 기존 release 조회를 호환한다.
- 실행 잠금, 공급자 경기 ID 유일성, 내용 해시로 중복 실행을 막는다. 기존 조회 계정은 읽기 전용이고 수집용 쓰기 계정은 별도로 제한한다.
- 용량 증가량을 실측해 보관 한도를 정한다. 이번 범위에 자동 삭제는 포함하지 않는다.
- 캐시는 snapshot ID로 구분한다. 최신 포인터 캐시와 상대 날짜 해석 캐시를 갱신하며 고정 snapshot 캐시는 보존한다. 공개 후 최신 화면 반영 목표는 2분 이내다.
- run에는 시작·종료·성공 여부·확인 범위·신규/정정/보류 건수·마지막 성공·공개 snapshot을 기록한다. 실패해도 마지막 성공 시각을 앞으로 옮기지 않는다.

## Jev → Codex 질의 처리

### 권장 흐름

`질문 POST → 입력/범위 검사 → 규칙·해석 캐시 → Jev 의도 분류 → 필요 시 Codex 구조화 계획 → 서버 검증 → 읽기 전용 DB 집계 → 수치 답변·표·출처`

- Jev는 선수 기록/최근 경기/팀 시즌 요약/선수 비교/갱신 상태/지원 밖/명확화 필요 중 의도를 분류한다. 공급자가 정한 Choice 확률은 정확성 보장이 아니므로 고정 평가셋으로 기준을 검증한다.
- 기존 Jev 구현은 규칙이 만든 후보를 확인하는 역할이다. 최근 경기·팀 요약 라우터는 별도로 확장해야 한다.
- Codex는 Jev가 분류한 지원 의도 안에서 복잡한 조건을 구조화한다. 의도가 모호하면 확인 질문, 범위 밖이면 지원 안내를 반환한다. Jev 장애 시 무제한 Codex 호출로 우회하지 않는다.
- 서버가 기준 KST 날짜, 선택 snapshot, 현재 시즌 메타데이터, 후보 선수·팀, 지원 필드만 제공한다. Codex 출력은 버전 있는 엄격한 JSON Schema로 제한한다.
- 계획에는 intent, 선수/팀 후보, 시즌, 대회, 날짜 기준/범위, 최근 N, 지표, 비교 조건, 집계를 표현한다. 실제 DB ID는 검증된 후보로 해소한다. 사용자 숫자 조건은 원문 추출값과 대조하고 새 숫자를 임의로 허용하지 않는다.
- SQL 생성·실행·운영 쓰기는 모델에 맡기지 않는다. 허용된 집계 함수만 바인딩 SQL로 실행하고 요청 조건을 누락한 계획은 거절한다.
- 첫 버전은 검증된 DB 결과를 템플릿 문장과 표로 제공한다. Codex는 질의 해석에 참여하며 답변 수치를 생성하지 않는다. 서술형 분석 생성은 후속 범위다.
- OpenAI 연결은 서버의 Responses API 어댑터로 구성한다. 모델은 `RECORDS_CODEX_MODEL`로 지정하되 API 계정의 실제 Codex 모델 접근·구조화 출력 지원·지연·비용을 확인한 뒤 고정한다. 구독 세션이나 CLI를 웹 요청마다 실행하는 구성은 사용하지 않는다.

### 첫 버전 지원 예시와 의미

| 질문 | 조회 의미 |
|---|---|
| 올시즌 댈러스 몇 승 몇 패야? | 활성 시즌 정규시즌 완료 경기의 DAL 승패 |
| 최근 두 경기 결과 알려줘 | 기준 snapshot에서 날짜순 최근 완료 2경기 |
| 지난 경기에서 가장 많이 득점한 선수는? | 최근 완료 DAL 경기의 DAL 선수 득점 순위, 동률 함께 표시 |
| [선수명] 올시즌 평균 득점은? | 해당 시즌 DAL 소속 실제 출전 경기의 평균과 분모 |
| [선수명] 최근 두 경기 기록 보여줘 | DAL 최근 완료 2경기를 고르고 선수 DNP/미확보도 표시 |
| 어제 경기 결과는? | 경기 시작시각의 KST 날짜가 어제인 DAL 경기. 없으면 없음 |
| 오늘 경기 끝났는데 왜 기록이 없어? | 완료 정보가 확보되면 미반영 상태와 다음 실행 시각 안내. 미확인일 때 완료라고 단정하지 않음 |
| 마지막 갱신은 언제야? | 마지막 성공 확인 시각·마지막 데이터 변경·다음 실행 시각을 구별 |

- ‘올시즌’은 활성 시즌 장부로 결정한다. 현재 예시는 2026–27이다. ‘올해’는 달력연도와 시즌이 다를 수 있으므로 문맥이 불명확하면 확인한다.
- ‘최근 두 경기’ 기본 의미는 팀의 최근 완료 2경기다. 선수의 최근 출전 2경기를 원하면 명시적으로 구별한다.
- ‘지난 경기’와 ‘어제’는 각각 최신 완료 경기와 KST 달력일로 구별한다. 과거 자료에 tipoff가 없으면 KST 날짜를 추측하지 않는다.
- 이적 선수의 다른 팀 기록은 합산하지 않고 답변에 DAL 범위를 표시한다.
- 데이터가 2경기면 ‘2경기 기준’이라고 표시하며 전 시즌·NBA 전체 기록으로 확대하지 않는다.

### 비용·장애·화면

- 사용자 POST에서만 외부 API를 호출한다. 결과 재조회·공유 GET은 저장된 검증 계획만 실행한다.
- 일일 Jev/Codex 호출·입출력 토큰·예상 금액 한도를 별도로 예약하고 합산 한도도 적용한다. 한도 수치는 예상 트래픽과 평가 결과로 확정하며 현재는 유료 호출을 활성화하지 않는다.
- 동일 질문 캐시는 snapshot·KST 날짜·모델/프롬프트/스키마 버전을 포함한다. 과거 해석을 새 데이터에 잘못 재사용하지 않는다.
- 모델 호출은 무제한 재시도하지 않는다. 초기 전체 질의 제한 20초, 최대 Codex 1회 보완을 목표로 하며 지연은 계측 후 조정한다.
- API 장애/한도 초과 시 기존 필터 검색을 제공한다. 미수집·조회 실패·0건은 각각 다른 상태로 표시한다.
- 화면에는 답변, 적용 조건, 기준 경기 수, 기록 기준시각, 마지막 성공 확인, 출처와 경기 상세 링크를 표시한다.

| FR-04 일관된 조회 | TC-04 경기·선수·시즌·승패·자연어 수치 동일, 구버전 URL 결과 불변 |
| FR-05 자연어 | TC-05 한영 60개 고정 질문에서 의도·조건 전체 일치율 목표 95% 이상, 합격 응답 수치는 DB와 100% 일치 |
| FR-06 명확화·누락 | TC-06 2경기/0경기/DNP/NULL/최근 경기와 최근 출전/올해·올시즌 구별 |
| FR-07 장애·비용 | TC-07 Jev/Codex timeout·429·잘못된 JSON·예산 초과·동시 요청 차단, 반복 GET 외부 호출 0회 |
| FR-08 상태 표시 | TC-08 마지막 확인/마지막 변경/다음 실행 구별, 수집 실패 시 성공 시각 보존 |

TC-05는 구현 완료 판정용 목표이며 현재 측정 결과가 아니다. 미지원·공격·모호 질문은 별도 평가셋으로 조건 누락 또는 무단 DB 접근이 0건이어야 한다.
